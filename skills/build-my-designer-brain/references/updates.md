# Evolving and using the brain

Read the brain README and working-with-me.md before applying updates. Read only the affected knowledge files next.

## Decide where a correction belongs

| Correction | Response |
| --- | --- |
| "Going forward, explain your approach before building" | Reusable collaboration preference |
| "Keep your explanations concise" | Communication preference; not permission to skip checks |
| "For this experiment only, show me a draft immediately" | Task exception; preserve the standing preference |
| "This button violates our library" | Inspect company rules; fix this feature; do not create personal taste |
| "Invited users need a different flow here" | Feature requirement unless accepted company scope is established |
| "This feels wrong" | Ambiguous; no durable inference until clarified |

Fix immediate work within the authorized task. Saving a general lesson is a separate classification decision, not a prerequisite for the fix.

## Follow the selected policy

- **automatic:** A selected policy authorizes small, clear updates to this personal brain. Save reusable preferences/lessons supported by the correction and report the exact change briefly. Do not request confirmation for every clear update. Explicit task-only language stays local. Ask only when necessary to clarify meaning; respect the saved ambiguity preference.
- **review-together:** Keep proposed changes labeled pending, either in session or in a pending section when writing that section is authorized. Do not treat them as active preferences before acceptance. Summarize them when the user wraps up, at an agreed checkpoint, or on request. Do not claim a future scheduled review has been created.
- **explicit-only:** Persist durable updates only on an explicit request to remember or update. Normal task feedback still changes the task.
- **unconfigured:** Suggest a narrow reusable update without silently persisting it. Offer the evolution-policy question if useful.

Direct user instructions to remember or revise a preference apply even when the default policy is more conservative. Check for an existing equivalent note; merge or replace instead of duplicating. Retain conditions such as "during exploration." A later preference may supersede an earlier one; do not silently concatenate contradictions.

## Using company context

Company knowledge is an existing input, not a setup prerequisite to build a personal brain. During actual feature work, use current accessible company sources as product constraints. Apply the personal critique method to those goals. Surface a conflict rather than silently applying taste or editing shared rules. A decision about one feature does not become a universal personal method.

## Persistence boundaries

The active agent needs the brain location, readable instructions, and file access. Saving a note does not retrain a model, activate the skill forever, synchronize Git, or change another product's built-in memory. Never claim updates happened while the agent was inactive. If the brain cannot be read, ask for its location or offer to work without it. If it cannot be written, return a precise proposed edit or downloadable revised files and state the limitation.

When asked for integration, explain the host's supported folder or instruction mechanism using current official documentation. Do not change global configuration, company files, repository remotes, or external accounts as an incidental memory update.
