# Brain output format

Create these files in the chosen brain folder. Use plain Markdown and relative links. Keep each as short as the answers permit. Never write personal answers into this skill's own folder.

## README.md

Include purpose, setup status (`draft`, `partial`, or `confirmed`), last-updated date, and links to the four files below. Record answered question IDs, explicit skips, unresolved questions, and next question while setup is partial; remove stale interview scaffolding once completed. Track confirmed choices separately from proposed defaults.

Include an instruction pointer for reuse:

> Read working-with-me.md and critique-methods.md before design work. Read references.md and lessons.md only where relevant. Follow the evolution policy in working-with-me.md. Personal taste does not override company requirements; surface conflicts. If you cannot access the relevant sources or save an update, say so.

This pointer must be given to the host agent to take effect. Do not claim that creating README.md automatically activates it across projects. Offer a short copyable pointer for the user's tool; modifying global instructions or company files is separate work requiring a request.

## critique-methods.md

Capture the user's starting lens, review method and sequence, exact priority order (including ties/partial/custom criteria), reason for emphasis, feedback style, role in suggesting solutions, output depth, and any repeated feedback they provided. Label unprovided items unconfigured. Explain that priority order guides attention, not exemption from important issues.

## working-with-me.md

Capture explanation-before-action, response length, assumptions/questions, alternative presentation, challenge style, checkpoints, additional habits, update policy, and ambiguity handling. Preserve conditional instructions and explicit exceptions.

For update policies, use stable labels `automatic`, `review-together`, `explicit-only`, or `unconfigured`, alongside the person's wording. Store the policy here, not in product-specific files. Include that persistence requires access and an active instruction to use the brain.

## references.md

If skipped: say "Not configured; personal taste and references were skipped." Do not populate inferred style.

For each supplied reference capture: source/path, what was actually inspected, user annotation, useful principle/detail, what not to borrow, and conditions where it fits. Record proposed style patterns separately from confirmed preferences. Distinguish public references from restricted company material; do not copy the latter into a personal repository.

## lessons.md

For each actual lesson record: context, observed result, interpretation, conditions/exceptions, source where appropriate, status, and update date. Mark superseded learning and link replacements. If none supplied, say "No lessons recorded yet" rather than inventing examples.

## Update notes and verification

For durable changes add a small dated note in the changed file: what changed, what user correction supports it, and the relevant scope. Keep notes concise, without copying full conversations. Edit an existing preference rather than accumulating conflicting copies. Log pending suggestions distinctly from accepted guidance under review-together mode.

After writes, read back affected content and check local links. Report paths and whether the content is draft, partial, or confirmed. If file tools are absent, provide equivalent Markdown or downloadable files and explain they still need saving. No fake persistence or claims of cross-tool synchronization.
